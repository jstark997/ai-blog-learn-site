# AI Blog & Learn

A single-author website about artificial intelligence, in two parts:

- **Blog** — essays: ideas, observations and commentary on AI.
- **Learn** — structured lessons, grouped into topics and ordered for reading,
  with interactive React demonstrations embedded in the prose.

It is a Next.js 16 application. Every word of editorial content is an MDX file
in `content/`, read from the filesystem at build time and rendered as static
HTML. **Git is the CMS**: writing is a file, publishing is a merge, and the
history of the site is the history of the repository. There is no database, no
backend service and no authentication — see
[Why there is no database, backend or authentication](#why-there-is-no-database-backend-or-authentication).

## Project structure

```text
content/              MDX — the source of truth for all editorial content
  blog/               one file per post; the filename is the URL slug
  learn/<topic>/      one directory per topic; one file per lesson
  pages/              standalone pages (About)

lib/content/          discovery, parsing, validation, ordering — no JSX
  schemas.ts          the Zod frontmatter schemas; the only definition of the fields
  blog.ts, learn.ts   retrieval, ordering, draft filtering
  pages.ts            standalone pages
  topics.ts           topic id -> title, order, description (presentation only)
  mdx.ts              the MDX pipeline: GFM, math, syntax highlighting
  env.ts              showDrafts — the single decision about draft visibility
  homepage.ts         what the homepage shows
  validate.ts         the rules shared by the build and validate:content

components/
  mdx/                prose components, server-rendered; registry.ts names them
  learn/              interactive demos — client components, lazily loaded
  blog/ lesson/ layout/ navigation/ home/ content/   UI

app/                  routes only; thin, no content logic
  blog/[slug]/        an article
  learn/[topic]/[lesson]/   a lesson
  sitemap.ts, robots.ts, rss.xml/route.ts

lib/site.ts           site name, copy, canonical URL helpers
scripts/              validate-content.mjs, verify.mjs, bundle-report.mjs
tests/                Vitest suite
```

Four invariants hold this together:

1. **Content is read from the filesystem at build time.** There are no
   `/api/*` routes for content, and nothing fetches content over HTTP.
2. **Server Components by default.** A Client Component exists only where there
   is real interactivity — currently the navigation links, the mobile menu and
   the demos.
3. **MDX carries prose; React carries interaction.** Neither leaks into the
   other: an MDX file imports nothing, and a component contains no editorial
   copy.
4. **`app/` is routing only.** Content logic lives in `lib/content/`.

## Authoring a blog post

1. Create `content/blog/<slug>.mdx`. **The filename is the URL**:
   `content/blog/why-attention-works.mdx` → `/blog/why-attention-works`. Use
   lower-case words separated by hyphens; there is no `slug` frontmatter field.
2. Write the frontmatter:

   ```mdx
   ---
   title: "Why Attention Works"
   description: "A short summary, used on the blog index, in page metadata and in the RSS feed."
   publishedAt: "2026-09-18"
   tags:
     - transformers
     - attention
   draft: true
   ---
   ```

3. Write the body in markdown. See [Writing in MDX](#writing-in-mdx) for what
   is available.
4. `pnpm dev`, and read it at `/blog/<slug>`. Drafts appear in development,
   marked with a **Draft** badge.
5. `pnpm validate:content` before committing.
6. Set `draft: false` when it is ready, and publish it — see
   [Publishing](#publishing).

A post needs no registration anywhere: the blog index, the homepage's recent
list, the sitemap and the RSS feed all discover it from the filesystem, and
order it by `publishedAt`, newest first.

Tags are labels, not links. Phase 1 has no tag pages, so a tag is a way of
telling the reader what a post is about, not a navigation surface.

## Authoring a lesson

A lesson lives in a topic directory, and **the directory name is the topic**.
There is no `topic` field in frontmatter and no `slug` field:
`content/learn/transformers/attention.mdx` → `/learn/transformers/attention`.

### Adding a lesson to an existing topic

1. Create `content/learn/<topic-id>/<lesson-id>.mdx`.
2. Write the frontmatter:

   ```mdx
   ---
   title: "Attention"
   description: "How a token decides which other tokens to read from."
   order: 30
   difficulty: "intermediate"
   prerequisites:
     - "transformers/embeddings"
   publishedAt: "2026-09-18"
   draft: true
   ---
   ```

   `order` positions the lesson within its topic and is **sparse — 10, 20,
   30…** — so that a lesson can later be inserted between two others without
   renumbering the topic. It must be unique within the topic;
   `pnpm validate:content` rejects a duplicate. It drives the topic listing,
   the sidebar and the previous/next pager.

   Each entry in `prerequisites` is a lesson path, `<topic-id>/<lesson-id>`,
   and must resolve to a lesson that exists. Prerequisites may cross topics.

3. Write the body, and embed a demonstration if one earns its place — see
   [Embedding an interactive demonstration](#embedding-an-interactive-demonstration).
4. `pnpm dev`, read it at `/learn/<topic>/<lesson>`, then
   `pnpm validate:content`.

### Adding a new topic

A topic is a directory plus three lines of presentation data:

1. Create `content/learn/<topic-id>/` and put at least one lesson in it.
2. Add an entry to `lib/content/topics.ts`:

   ```ts
   {
     id: "transformers",          // must equal the directory name
     title: "Transformers",
     order: 2,                    // position on the Learn index
     description: "The architecture behind modern language models.",
   }
   ```

`topics.ts` is presentation data only — it does not create a topic, it names
one. A directory with no entry, or an entry with no directory, is a
`pnpm validate:content` error rather than a half-configured topic on the Learn
index.

No code changes anywhere else: the Learn index, the topic page, the sidebar and
the pager are all built from the filesystem plus that file.

## Frontmatter reference

Frontmatter is validated with Zod (`lib/content/schemas.ts`) and the schemas are
**strict**: an unknown key is an error, not something quietly ignored. A
misspelt `drafts: true` would otherwise publish an unfinished piece in silence.

Every date field is an ISO `YYYY-MM-DD` date. **Quote it.** An unquoted YAML
date parses as a timestamp, and an impossible one (`2026-02-30`) is rejected
rather than rolled over into March.

### Blog post — `content/blog/*.mdx`

| Field | Type | Required | Default | Notes |
|---|---|---|---|---|
| `title` | string | yes | — | must contain actual words |
| `description` | string | yes | — | blog index, page metadata, RSS feed |
| `publishedAt` | ISO date | yes | — | the blog orders on this, newest first |
| `updatedAt` | ISO date | no | — | shown when it differs from `publishedAt` |
| `tags` | string[] | no | `[]` | labels, not links |
| `draft` | boolean | no | `false` | see [Drafts](#drafts) |

### Lesson — `content/learn/<topic>/*.mdx`

| Field | Type | Required | Default | Notes |
|---|---|---|---|---|
| `title` | string | yes | — | |
| `description` | string | yes | — | lesson cards, page metadata |
| `order` | positive integer | yes | — | sparse (10, 20, 30…), unique within the topic |
| `difficulty` | `"beginner"` \| `"intermediate"` \| `"advanced"` | no | — | shown on the lesson and its card |
| `prerequisites` | string[] of `<topic-id>/<lesson-id>` | no | `[]` | each must resolve to a real lesson |
| `publishedAt` | ISO date | yes | — | |
| `updatedAt` | ISO date | no | — | |
| `draft` | boolean | no | `false` | |

Deliberately absent: `topic` and `slug`. Both derive from the path, and a
second source of truth for a route is a typo away from splitting a topic in
two.

### Standalone page — `content/pages/*.mdx`

| Field | Type | Required | Notes |
|---|---|---|---|
| `title` | string | yes | |
| `description` | string | yes | |
| `updatedAt` | ISO date | no | |

Narrower on purpose. A page is not part of a chronology, so it has no
`publishedAt`; it is not in a reading order, so it has no `order`; and it has
no `draft`, because a page is reachable from the site navigation on every
route — an unfinished one is not committed.

## Writing in MDX

The body of every content file is MDX: markdown, plus the components named in
the registries. **An MDX file may not import anything.** Components reach the
content only by being registered, which is what keeps a content file from
pulling arbitrary code into a page — and what makes an unregistered component
name a build error rather than an element that silently renders as nothing.

Markdown itself gets:

- **GitHub-flavoured markdown** (`remark-gfm`): tables, strikethrough, task
  lists, autolinks.
- **Mathematics** (`remark-math` + KaTeX): `$inline$` and `$$display$$`,
  typeset at build time. No formula renderer is shipped to the browser. Wide
  display equations scroll horizontally and are keyboard-focusable.
- **Syntax highlighting** (`rehype-pretty-code` + Shiki) on fenced code blocks,
  highlighted at build time in both a light and a dark theme at once; switching
  theme re-highlights nothing. A fence with no language renders as plain text.

### Prose components — available in every content file

Registered in `components/mdx/registry.ts`. All server-rendered; a page using
only these ships no component JavaScript.

| Component | Props | What it is |
|---|---|---|
| `<Callout>` | `variant?: "note" \| "warning"`, `title?: string` | an aside inside prose. Carries a visible label, so the meaning survives without colour. |
| `<Equation>` | `label?: string`, `caption?: React.ReactNode` | a numbered, captioned display equation; put the `$$…$$` block inside it |
| `<Figure>` | `src`, `alt`, `width`, `height`, `caption?`, `priority?` | an optimized image via `next/image`. The dimensions are required — they reserve the space so the text does not jump. |
| `<ExternalLink>` | anchor props, `href` required | a link off-site, marked as such |

Three markdown elements are overridden too, so ordinary markdown syntax gets
the right behaviour with no ceremony: `a` (internal links route through
`next/link`, external ones are marked), `img` (plain, lazy, no layout shift —
`<Figure>` is the optimized path when you know the dimensions), and `table`
(wrapped so a wide table scrolls inside its own box rather than the page).

Example:

```mdx
<Callout variant="note" title="Worth knowing">

Anything in here is ordinary markdown, including `code` and $x^2$.

</Callout>

<Equation label="(1)" caption="Scaled dot-product attention.">

$$
\operatorname{Attention}(Q, K, V) = \operatorname{softmax}\!\left(\frac{Q K^{\top}}{\sqrt{d_k}}\right) V
$$

</Equation>

<Figure
  src="/images/learn/attention-heads.png"
  alt="Four attention heads, each attending to a different span of the sentence."
  width={1200}
  height={720}
  caption="One head per row."
/>
```

Images referenced this way are static files: put them under
`public/images/blog/` or `public/images/learn/` and reference them from the
root, `/images/...`.

> **Placeholder rule.** The sample posts and lessons in this repository are
> scaffolding written by a coding agent, not editorial writing. Each one opens
> with a `<Callout variant="warning" title="Placeholder content">` saying so.
> An agent must not publish editorial prose without that marker; the author
> writes the real thing and removes the callout.

### Embedding an interactive demonstration

Demos are registered separately, in `components/learn/registry.ts`, and that
registry is given **only to lesson pages**. An article can never embed one, and
no demo code reaches an article's bundle.

Available today:

| Demo | Lesson it was built for |
|---|---|
| `<ActivationFunctionExplorer />` | `neural-networks/activation-functions` |
| `<GradientDescentDemo />` | `neural-networks/gradient-descent` |

Write it as a block on its own line in the lesson body:

```mdx
Choose a function and drag the input.

<ActivationFunctionExplorer />
```

Each demo's JavaScript is fetched only by the lessons that actually render it:
a lesson with no demo fetches none. That property depends on one rule, so it is
worth stating plainly.

**Adding a new demo:**

1. Write the component under `components/learn/<topic>/<Name>.tsx`. It is a
   Client Component: `"use client"` at the top, and a **default export** (the
   lazy loader resolves to it).
2. Add a loader to `components/learn/lazy-demos.ts`:

   ```ts
   export const MyDemo = dynamic(() => import("@/components/learn/<topic>/MyDemo"));
   ```

3. Name it in `components/learn/registry.ts`, importing **from
   `lazy-demos.ts`, never from the component file directly**. A direct import
   in either file puts that demo's JavaScript back on every lesson page,
   silently — the two tests in `tests/` that guard this check both halves of
   the rule for that reason.
4. Add a test. A demo is interactive code; the suite drives it with
   `@testing-library/user-event`.

A demo should explain something prose cannot. Interactivity for its own sake is
not a reason to build one.

## Drafts

`draft: true` on a post or a lesson means unpublished. What that does depends
on where the site is running, and **one helper decides it everywhere** —
`showDrafts` in `lib/content/env.ts`. No component, route, sitemap entry or
feed item reads `NODE_ENV` for this.

| Where | Drafts |
|---|---|
| `pnpm dev` | visible, and badged **Draft** wherever they appear |
| a preview deployment (branch or pull request) | visible and badged — a preview URL is exactly where an unfinished piece needs reviewing, for maths, diagrams and responsive layout |
| production | invisible: not listed, not linked, not in the sitemap, not in the RSS feed, and **the URL returns 404** |
| anywhere, with `SHOW_DRAFTS=true` / `=false` | as set — the host-neutral override |

A preview deployment is a *production* Next.js build, so `NODE_ENV` alone
cannot tell the two apart; `VERCEL_ENV` is what separates `production` from
`preview`.

The 404 is enforced twice on both content routes: `dynamicParams = false`, so
Next will not render a path `generateStaticParams` did not list, and a
`notFound()` guard in the page itself. Either alone is not enough, and
`pnpm verify` asserts the real status code against a real server for every
draft in `content/`.

To check production behaviour locally:

```bash
pnpm verify              # builds and probes with drafts hidden
SHOW_DRAFTS=false pnpm build && pnpm start
```

## Testing and the validation gate

```bash
pnpm lint
pnpm validate:content
pnpm test
pnpm build
pnpm verify        # anything touching routing, drafts or SEO
```

All of it must pass before a change is done — "the code looks right" is not the
bar.

**`pnpm validate:content`** walks `content/` eagerly and checks what a single
file cannot check about itself: frontmatter against the schemas, the rule that
an MDX file imports nothing, topic directory ↔ `topics.ts` parity, `order`
uniqueness within a topic, prerequisite resolution, and blog slug uniqueness.
It exits non-zero on invalid *published* content, and it runs as `prebuild`, so
a broken post cannot reach a deployment. An invalid **draft** warns and is
skipped — an unfinished draft must not block the deployment of unrelated
published work.

**`pnpm test`** is Vitest with jsdom and Testing Library. The suite covers the
content utilities against fixture trees, the MDX pipeline, every route's
rendering, the demos driven through real user events, draft leakage, the
sitemap and feed, and colour contrast. Tests live in `tests/`.

**`pnpm verify`** builds the application, serves it on a free port with
`SHOW_DRAFTS=false`, and asserts status codes and page content for every route
— derived from `content/`, not hard-coded, so adding a post or a lesson extends
the check automatically. It then shuts the server down. This is the
agent-safe way to confirm the site actually serves.

## Publishing

Git is the publishing mechanism. Writing is a commit; publishing is a merge.

```text
feature/new-attention-lesson
          ↓ push
  pull request → preview deployment
          ↓ review: maths, diagrams, responsive layout, demos
        merge to main
          ↓
   production deployment
```

1. Branch: `git switch -c feature/<what-you-are-writing>`.
2. Write, with `draft: true` while it is unfinished.
3. Run the gate: `pnpm lint && pnpm validate:content && pnpm test && pnpm build`.
4. Commit. Commit messages follow
   [Conventional Commits](https://www.conventionalcommits.org/) — `feat(blog):`,
   `fix(learn):`, `docs:`. A pull request is titled with its primary commit's
   subject.
5. Push and open a pull request. The preview deployment shows the branch
   **with drafts visible** — this is where formatting, mathematics, diagrams
   and demos get reviewed.
6. Set `draft: false` and push again when the piece is ready.
7. Merge to `main`. The production deployment follows automatically, with
   drafts hidden.

Publishing a post requires no other change anywhere: the index, the homepage,
the sitemap and the RSS feed pick it up from the filesystem.

## Deployment

The site is a static-by-default Next.js application and deploys to Vercel.

**One-time setup** (a human does this — it needs accounts the build cannot
have):

1. Create the GitHub repository and push `main` to it.
2. Create the Vercel project and link it to the repository. The framework
   preset is Next.js; the install command is `pnpm install --frozen-lockfile`
   and the build command is `pnpm build`.
3. Set `NEXT_PUBLIC_SITE_URL` in the Vercel project — to the production domain
   for the production environment. Without it, canonical URLs, the sitemap and
   the feed point at `localhost`.
4. Configure the production domain.

Afterwards: every pull request gets a preview deployment with drafts visible,
and every merge to `main` deploys to production with drafts hidden. Draft
gating keys off `VERCEL_ENV`, so this works with no per-environment
configuration — leave `SHOW_DRAFTS` unset.

Continuous integration runs the same gate — `pnpm install --frozen-lockfile`,
`pnpm lint`, `pnpm validate:content`, `pnpm test`, `pnpm build` — on every pull
request and every push to `main`. The workflow, `.github/workflows/ci.yml`, is
added with the deployment setup above; until then the gate runs locally.

## Architecture

### The path from a file to a page

```text
content/**/*.mdx
      ↓  gray-matter — split frontmatter from body
      ↓  Zod (lib/content/schemas.ts) — validate, or fail the build
      ↓  showDrafts — is this visible here?
      ↓  next-mdx-remote/rsc — compile in a Server Component
      ↓      remark-gfm, remark-math
      ↓      rehype-katex, rehype-pretty-code (Shiki)
      ↓  a registry: prose components, plus demos for a lesson
      ↓
static HTML, generated at build time
```

Everything expensive happens at build time. KaTeX, Shiki, MDX, `gray-matter`
and Zod are all server-side; none of them appear in any client bundle. The
JavaScript a reader downloads is React, the Next runtime, the navigation, and —
on a lesson that has one — that lesson's demo.

### Why there is no database, backend or authentication

This is not a shortcut to be paid off later. It is the right architecture for
what the site currently does.

- **No database.** The content is a few dozen MDX files written by one person
  and reviewed in pull requests. Git already provides authorship, history,
  branching, review and rollback — everything a CMS would offer, with better
  tooling and no operational surface. A database would add a service to run, a
  schema to migrate and a backup to worry about, and would take the content
  *out* of the pull request where it is reviewed. It earns its place when
  there is persistent *application* data — lesson progress, saved experiments,
  quiz scores, comments — and not before. Editorial content stays in MDX even
  then.
- **No backend.** Every page can be generated statically, so there is nothing
  for a server to decide at request time. Interactive demonstrations run the
  mathematics in the browser, where the feedback is immediate and the hosting
  is free. A Python service earns its place when a lesson needs computation the
  browser genuinely cannot do — real tokenization, embeddings, model inference.
- **No authentication.** Authentication exists to distinguish users, and
  nothing here is per-user: the blog and the lessons are public, and are meant
  to stay public. Adding it in anticipation of a future database would mean
  maintaining a login flow, session handling and an account lifecycle that no
  current feature reads. It earns its place with the first personalized
  feature.

The rule underneath all three: **do not add infrastructure before it solves a
requirement that exists.**

### Where it extends

The progression the specification anticipates, in order:

```text
Next.js + MDX          ← today
      ↓
interactive React      ← today
      ↓
FastAPI                when a lesson needs Python-side computation:
                       tokenization, embeddings, PyTorch inference,
                       transformer inspection
      ↓
PostgreSQL + auth      when persistence is useful: progress, saved
                       experiments, quiz history, preferences
      ↓
an AI tutor            explain this differently, quiz me, compare these two —
                       augmenting the structured content, not replacing it
```

A future FastAPI service would sit behind the interactive components only —
demo → FastAPI → the Python AI stack — and the content architecture would not
depend on it. Each step is additive: none of them requires rewriting how
content is stored, validated or rendered, which is the property the current
structure exists to preserve.

## For coding agents

Read `CLAUDE.md` first — it is the standing contract, and it is short. In
summary: pnpm only; never run `pnpm dev` or a foreground `pnpm start`; do not
edit the specification or the plan; append every decision to
`docs/decisions.md`; read `package.json` for installed versions rather than
